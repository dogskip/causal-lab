# CRDT·동기화 검증 도구의 재사용 범위 조사

## 판단 요약

현재 프로젝트에서 재사용 가치가 가장 큰 부분은 가상 시간, 고정 난수, 사건의 전체 순서, 실행 기록이다. 실행기가 외부 CRDT의 실제 변경과 메시지를 처리하고, 사용자가 정의한 업무 규칙을 검사하며, 실패 입력을 파일로 재생할 수 있을 때 개발팀용 도구가 된다. 현재 실행기는 `Replica`를 직접 생성하고 자체 `Operation`만 전달하므로 그 연결은 아직 없다. 이 제안은 사용자 목적과 현재 코드의 차이에 대한 **설계 추론**이다. [C01, C02]

추천 범위는 **한 과정에서 실행할 수 있는 결정적 CRDT·동기화 시험**이다. 외부 대상 하나의 연결을 먼저 입증한 다음 공통 실행 명세를 확정한다. Yjs 원시 변경과 Automerge sync에는 서로 다른 전달 전제가 있으므로 모든 대상에 같은 손실·중복·순서 교체 규칙을 적용하면 오판한다. FoundationDB 사례도 실제 코드를 실행하고 시간·통신·난수를 제어하는 것이 핵심이며, 그 방법 자체가 모든 외부 구현의 재현을 보장하지는 않는다. [S01, S06, S07]

새로운 CRDT, 운영 동기화 서비스, 실제 서버의 장애 유발 기능, 모든 상태를 탐색하는 검사기를 이번 목표에 추가할 근거는 없다. fast-check와 AMC는 이미 입력 생성·축소와 실제 Automerge의 상태 탐색을 제공한다. Causal Lab의 차별성 후보는 TypeScript 개발팀이 자기 구현과 업무 규칙을 연결하여 실패를 재현하고 자동 검사에 결과를 전달하는 좁은 사용 절차다. **차별성 후보이며 사용 수요나 성능 우위를 입증한 주장이 아니다.** [S04, S05, C01]

## 조사 범위와 증거 수준

조회일은 모두 **2026-10-14**다. 공식 문서·명세, 저자의 논문, 해당 프로젝트의 원본 코드만 판단에 사용했다. 검색 결과의 제품 소개나 제삼자 설명으로 능력을 확정하지 않았다. 오래된 저자 논문은 원리와 한계의 근거이며 최신 제품 능력의 근거가 아니다. [S01–S20]

| 구분 | 이 문서가 입증하는 범위 | 입증하지 않는 범위 |
| --- | --- | --- |
| 현재 코드 | 아래 SHA-256에 해당하는 구조, 공개 함수, 저장 계약 | 외부 구현 연결, 실제 장치·운영환경 적합성 |
| 공식 자료 | 각 도구의 설명된 능력과 전제 | Causal Lab에 연결했을 때의 동작이나 성능 |
| 설계 추론 | 목표와 근거에 맞는 최소 범위 및 반례 | 구현 완료, 전수 정확성, 보편적 신뢰성 |
| 후속 실험 | 대상·버전·입력·관찰값을 고정한 실행 증거가 필요함 | 이 조사 문서만으로 통과 판정 |

이 문서는 3심 검토의 근거 자료다. 문서 조사, 반례 검토, 실제 연결·실패 재생 검증을 서로 다른 판단으로 기록해야 하며, 이 문서 작성만으로 세 검토가 통과했다고 처리하지 않는다. Jepsen도 유한한 시험으로 오류의 부재를 증명할 수 없고 검사 코드 자체에 오류가 있을 수 있음을 명시한다. 따라서 신뢰도는 검증한 조건과 반복 가능한 증거로 표현한다. [S03]

## 외부 구현을 연결하기 위한 최소 계약

다음은 **제안**이며 공개 API가 이미 존재한다는 뜻이 아니다. 최소 한 실제 외부 대상의 실험이 통과한 뒤 함수와 자료형을 확정해야 한다. [C02, S01, S06, S07]

| 책임 | 최소 계약 후보 | 필요한 이유·근거 |
| --- | --- | --- |
| 대상 초기화 | 대상 ID·정확한 버전, 연결 코드 버전, 복제본 ID, 초기 문서, 설정, 실행 내 고유 식별자를 명시한다 | 대상의 숨은 난수와 시각이 seed 재현을 깨뜨릴 수 있다. [S09–S13] |
| 지역 변경 | 프로젝트의 업무 연산을 입력으로 받고 실제 대상에 적용한다. 입력·수락 결과·생성 메시지를 기록한다 | 자체 `Replica`를 다시 시험하는 것만으로 외부 구현의 정확성을 판단할 수 없다. [C02, S01] |
| 메시지 | 실행기는 `Uint8Array` 등 불투명한 본문과 출발·도착·연결 ID·순서·시각을 처리한다 | Yjs와 Automerge는 이진 메시지를 사용한다. 실행기가 대상의 내부 형식을 다시 구현할 이유가 없다. [S06, S07, S13] |
| 전달 전제 | 원시 변경과 순서 보존 연결을 구분하고, 대상이 허용하지 않는 장애 설정을 실행 전에 거부한다 | Yjs 변경은 중복·순서 교체를 허용한다. Automerge sync는 신뢰할 수 있는 순서 보존 전달을 전제한다. [S06, S07] |
| 재연결 | 연결 해제·새 연결의 범위, 이전 연결 메시지 처리, 대상의 sync 상태 초기화 정책을 명시한다 | 새로운 연결과 기존 메시지의 임의 재전송은 같은 동작이 아니다. 대상이 공식적으로 정의한 재연결 절차를 사용해야 한다. [S07, S12] |
| 관찰 | 대상이 제공한 JSON 관찰값과 검사에 필요한 대상별 보조값을 반환한다. 실행기는 별도 규칙으로 비교한다 | 내부 저장 바이트가 다르더라도 문서 관찰값은 같을 수 있다. 반대로 관찰 항목이 지나치게 적으면 결함을 감출 수 있다. 이 판단은 CRDT의 상태 동등성 정의에 따른 추론이다. [S06, S14] |
| 진행 종료 | 처리 사건·전달 메시지·가상 시간의 상한과 종료 이유를 기록한다. 합의된 안정 전달 조건에서만 복구 기한을 검사한다 | 대기열이 비었다는 사실만으로 삭제된 메시지의 복구나 문서 수렴을 입증하지 못한다. [C02, S01, S06] |
| 정리 | 대상의 종료 함수로 관찰자·상태를 해제한다. 저장과 HTTP는 실행기 밖에 둔다 | Y.Doc는 destroy API가 있고 현재 프로젝트도 저장을 별도로 둔다. [S09, C03] |

첫 연결은 동기식 API로 완료되는 작은 문서 연산으로 제한하는 방안이 합리적이다. 임의 Promise·실제 소켓·실제 시각을 그대로 허용하면 현재 가상 시간의 보장 범위가 달라진다. 비동기 순서 검사는 fast-check의 별도 진행 방식이 있으므로 실제 요구가 확인되기 전까지 자체 범용 비동기 실행기를 추가하지 않는다. **최소 범위에 대한 추론**이다. [C02, S04]

### 전달 전제의 핵심 반례

**Yjs 원시 변경:** 변경은 교환법칙·결합법칙·멱등성을 만족하며 모든 변경을 수신해야 수렴한다. 누락한 변경을 전달하지 않고 마지막 상태가 같기를 기대하는 시험은 이 전제에서 벗어난다. 복구 과정은 Yjs의 전체 상태 또는 상태 벡터 차이 교환을 실제로 호출해야 한다. 실행기가 정답 문서로 대상을 직접 덮어쓰면 복구 결함을 감춘다. [S06]

**Automerge sync:** 한 쌍의 문서마다 sync 상태를 유지하고 수신 후 다음 메시지를 생성한다. 이 절차에 내부 메시지 손실·중복·순서 교체를 임의로 넣고 복구되지 않았다는 이유만으로 구현 오류를 선언하면 문서의 신뢰할 수 있는 순서 보존 연결 전제를 어긴다. 연결 해제·재연결과 메시지 전달을 구분해야 한다. [S07, S12, S13]

현재 `healAll()`은 보관한 사건과 모든 자체 연산을 손실 없는 경로로 다시 전달한다. 이 방식은 자체 OR-map의 증거이며 외부 대상이 같은 복구 능력을 갖는다는 증거가 아니다. `heal`의 구현을 외부 대상으로 일반화하기 전에, 그 대상의 실제 동기화 절차를 호출하는 연결 계약이 필요하다. [C02]

## 식별자·시간·초기 상태의 재현성

| 대상 | 공식 API·원본 코드의 사실 | 격리한 시험에 대한 제안 | 남아 있는 확인 |
| --- | --- | --- | --- |
| Yjs 13.6.27 | `Doc` 생성 시 clientID를 난수로 정하고 guid도 기본적으로 난수다. 공식 API는 clientID를 readonly로 표시한다. 공식 FAQ는 속성 교체 방법과 중복 ID로 인한 영구 손상 가능성을 설명한다. 원본 시험 코드가 변경 전에 `y.clientID = i`를 지정한다. [S09, S10] | 시험 전용 문서에서만 고유 clientID와 guid를 명시하고 모든 변경 전에 확정한다. 대상에 저장된 과거 clientID와도 충돌하지 않게 한다. 이 조치는 실제 사용자 식별자 관리 방식으로 권장하는 것이 아니다 | 실행 반복 간 메시지·관찰값의 동일성. ID 충돌 시 대상이 새 난수 ID를 생성하므로 시험이 충돌을 감지하고 중단하는지 확인해야 한다. [S10] |
| Automerge | `init`와 `clone`은 actor를 명시할 수 있다. `change`의 time을 생략하면 현재 시각을 사용한다. 원본 sync 시험은 고정 actor와 `{ time: 0 }`을 사용한다. [S11, S12] | actor·초기 문서·설정을 기록한다. 모든 변경과 emptyChange에 가상 시각 또는 고정 time을 명시한다. 새 문서·clone·load에도 actor 규칙을 적용한다 | 고정된 제품 버전에서 변경 해시·메시지·관찰값의 재현성. 공식 예제로 연결 가능성이 확인되지만 Causal Lab 연결이 통과한 것은 아니다 |

따라서 재생 입력은 seed 하나로 끝나지 않는다. 최소한 시나리오, 난수 방식과 버전, 실행기 버전, 대상과 연결 코드의 정확한 버전·해시, 초기 문서·설정·식별자·시간 규칙, 전달 전제, 검사 규칙의 ID·버전이 필요하다. 이 목록은 외부 구현의 결정성 전제와 실패 축소 재생 조건에서 산출한 **설계 제안**이다. 기존 v1 시나리오 ID를 새 뜻으로 바꾸면 이전 기록을 혼동하므로 새 계약은 새 버전으로 구분한다. [S01, S04, S09–S12, C04]

## 수렴과 업무 규칙을 독립적으로 검사하기

CRDT의 정의는 같은 변경 집합을 받은 복제본의 상태 동등성을 요구한다. 그것만으로 응용의 업무 규칙이 성립하지는 않는다. 예를 들어 모든 복제본이 공통된 빈 문서로 끝나면 상태는 같지만 수락한 자료가 누락됐을 수 있다. AMC가 응용별 속성을 별도로 정의하는 이유와 같다. [S14, S05]

| 검사 종류 | 최소 판정 | 오판을 방지할 조건 |
| --- | --- | --- |
| 대상 수 | 요청한 복제본 ID·개수와 관찰 결과의 ID·개수가 일치한다 | 동등성 비교에서 복제본 하나가 누락되면 안 된다. 현재 판정은 `Object.values(states)`를 비교하므로 별도 검사 후보가 된다. [C02] |
| 관찰값 동등성 | 선택한 관찰 명세에 따라 모든 복제본의 값을 비교한다 | 대상 자체의 `converged`나 동일 실행기의 계산만 신뢰하지 않는다. [C02, S14] |
| 자료 보존 | 수락한 연산에 대해 그 대상의 업무 의미를 검사한다 | 자체 OR-map의 동시 값 보존 규칙을 다른 CRDT에 일괄 적용하지 않는다. [C02, S05, S14] |
| 삭제·순서·참조 | 사용자가 실제 요구한 규칙을 입력 이력과 결과로 검사한다 | 대상의 충돌 처리 규칙과 같은 코드를 검사기에서 재사용하면 같은 오해를 공유할 수 있다. [C05, S04, S05] |
| 복구 | 장애 종료 후 합의된 전달 조건과 기한에서 규칙을 검사한다 | 손실 허용 기간과 복구 검증 기간을 명시한다. 모든 메시지 전달을 요구하는 대상 전제를 유지한다. [S01, S06, S07] |
| 도구의 오판 방지 | 의도적으로 메시지·자료를 누락하거나 잘못된 관찰값을 반환하는 대상이 확실히 실패한다 | 정상 예제만 통과하면 검사기의 감지 능력을 알 수 없다. 시험 코드에도 오류가 있을 수 있다는 한계에 대한 제안이다. [S03] |

현재 독립 기대값도 자체 OR-map의 같은 문서 규칙을 다시 구현하므로 규칙 해석 오류를 공유할 수 있다고 명시한다. 새 연결에서는 대상의 생성 코드와 검사 코드를 구분하고, 실제 업무 의미의 예제·반례를 추가해야 한다. 그러한 독립성 없이 검사 횟수만 늘리는 것은 검증 범위를 늘렸다는 주장에 충분하지 않다. [C05]

## 실패 재생과 자동 검사 결과

fast-check는 일반 재생에 seed/path를, 모델 명령 재생에는 replayPath를 추가로 요구한다. 따라서 단순 오류 문자열만 저장하지 않고 검사 결과의 구조화된 정보를 보관한다. 축소 결과는 같은 실패 규칙이 여전히 실패하는지 다시 실행해야 하며, 원래 입력도 함께 유지한다. **공식 재생 계약에서 산출한 제안**이다. 현재 의존성은 `^3.23.2`이므로 최신 문서의 API를 확인 없이 도입하지 않고 실제 사용 버전에 맞춰 확정한다. [S04, C01]

최소 결과 묶음은 입력 명세, 실행 환경 명세, 결과, 실행 기록, 실패 규칙, 실제로 실패하는 축소 입력이다. 축소가 끝나지 않았으면 그 사실을 표시한다. 모든 파일의 이름·바이트 수·SHA-256을 검증하고, 실제 메시지 본문이 재생에 필요하면 그 본문도 포함한다. 파일 해시는 내용 동일성을 확인하며 구현 정확성이나 작성자 인증을 대신하지 않는다. 이 자료 계약은 **제안**이다. [S04, S15, S17]

자동 검사 상태는 `pass`, `fail`, `inconclusive`, `error`를 구분하는 방안이 적합하다. 통과는 요청한 모든 실행과 필수 규칙을 검사했을 때만 허용한다. 사건 상한·시간 제한·지원하지 않는 전달 설정·재생 불일치·검사기 오류를 통과로 축약하면 안 된다. fast-check도 시간 제한으로 예정 횟수 전에 중단했을 때 기본 설정에 따라 성공으로 처리될 수 있다고 명시한다. 종료 코드와 중단 처리의 정확한 대응은 프로젝트 설계에서 별도로 확정한다. [S04]

GitHub Actions의 결과 파일 보관은 이 목적에 맞는 기존 기능이다. 파일을 저장·다운로드하고 SHA-256을 검증하는 기능이 있으므로 별도 결과 서버가 초기 필수 기능일 이유는 없다. 다만 다운로드 검증 불일치가 경고로 표시될 수 있어, 프로젝트 자체 재생 검증은 해시 불일치를 명시적으로 실패 처리해야 한다. 결과의 공개·전송은 별도 사용자 승인 범위다. [S17]

### DB와 열에 대한 최소 판단

현재 `scenarios`, `runs`, `schema_migrations`는 자체 시나리오와 불변 실행 결과를 보관한다. 모든 시험마다 DB를 요구하면 실패 공유·자동 검사 연결에 새로운 설치 의존성이 생긴다. 따라서 **파일 결과를 기본으로 하고 SQLite를 선택 기능으로 유지**하는 방안을 추천한다. 이 판단은 사용자 목적과 현 구조에 따른 추론이다. [C03, S17]

외부 대상 결과를 DB에도 보관할 경우 필요한 자료는 다음과 같다. 아래 이름은 설계 후보이며 지금 DB에 해당 열이 있다는 뜻이 아니다. 기존 v1 표의 해시 의미를 변경하지 않고 새 버전의 결과 저장 계약을 정해야 한다. [C03, C04]

| 자료 | 필요한 값 | DB 후보·중복 방지 조건 |
| --- | --- | --- |
| 시험 정의 | 정의 ID, 계약 버전, 정규 JSON, 바이트 수 | `verification_cases` 또는 새 버전 정의 표. 정의 ID는 완전한 정규 내용에 결합한다 |
| 재현 가능한 실행 결과 | 결과 ID, 정의 ID, 상태, 결과 JSON, 환경·대상·연결·검사 명세, 실제 처리량, 종료 이유 | `verification_runs` 또는 새 버전 결과 표. 환경·대상 명세를 포함한 내용으로 ID를 계산한다. 정의 ID에 외래 키를 적용한다 |
| 파일 결과 | 파일 이름, 인코딩, 바이트 수, 해시, 본문 | 초기에는 결과 묶음 안에 보관한다. 별도 조회 요구가 없다면 파일마다 표를 추가하지 않는다 |
| 조회용 열 | 상태·정의 ID·대상 ID 등 실제 조회 조건 | 결과 JSON과 중복되는 열은 저장 시 그 내용과 일치해야 한다. 조회 요구 없는 열·색인은 추가하지 않는다 |

시각·자동 검사 URL·실제 소요시간은 실행 환경의 관찰 자료다. 동일 시나리오의 결정적 결과와 별도 검사 실행 기록을 구분해야 하며, 이런 값 때문에 동일 결과의 불변 ID가 매번 달라지지 않도록 설계해야 한다. 작업자·계정·조직·권한·알림·과금 표를 추가할 사용 요구는 확인되지 않았다. **이번 범위에 대한 판단**이다. [C03, S01, S17]

## 확정 전에 필요한 검증

- 실제 외부 구현 하나를 정확한 버전으로 고정하고 지역 변경·전달·복구·관찰을 연결한다. 예제만으로 대상 전제가 충족됐다고 간주하지 않는다. [S06, S07]
- 같은 초기 식별자·시각·입력·환경으로 반복하여 관찰값과 기록이 동일한지 확인한다. 무작위 기본값을 유지한 비교도 함께 실시해 재현 계약이 실제로 필요한지 확인한다. [S09–S12]
- 정상 대상의 통과, 의도적 자료 누락의 실패, 미완료 실행의 비통과, 해시·대상 버전 불일치의 재생 거부를 확인한다. 이 요구는 도구 자체 오류와 유한 시험의 한계에 대한 대응 제안이다. [S03, S04]
- 모델별 허용 전달 순서와 재연결을 확인한다. 허용하지 않는 설정은 대상 오류로 보고하지 않는다. [S06, S07]
- 실패 입력을 별도 과정에서 재생하고 같은 규칙이 실패함을 확인한다. seed/path만으로 부족한 초기 정보는 결과 명세에 추가한다. [S04, S09–S12]
- SQLite를 사용하지 않는 과정에서 실행·실패 재생·파일 공유가 가능해야 한다. 저장 재열기는 저장 계약의 증거이고 대상 정확성의 증거가 아니다. [C03, S17]

이 검증이 끝나기 전에는 범용 연결 지원, 제품 수준의 정확성, 업계 제품보다 높은 신뢰성, 100점의 품질을 확정하지 않는다. 시험한 조건·관찰한 실패·알려진 한계가 판단의 범위다. [S03]

## 2026-10-14 설계 실험과 검토 보충

조사 이후 부모 담당이 Yjs 13.6.27을 별도 임시 설치하여 실제 자기 문서의 encodeStateAsUpdate 전체 상태 교환을 실행했다. 256 seed × 2회 반복, 완전 복구의 잘못된 명령 해석 검출, 복구 미완료의 inconclusive, 정상·실패·미완료의 별도 Node 과정 재생, 관찰값 분리·동결, 대상별 같은 키 충돌 의미, 코드·버전·패킷·초기화 불일치 거부가 통과했다. 결과는 [yjs-results.json](evidence/2026-10-14/yjs-results.json)이다. 첫 버전의 단순 패킷 재전송과 미기록 오류는 2심 반례로 폐기했다. 이 실험은 제안 공통 API나 제품 전체의 합격을 입증하지 않는다.

SQLite 3.53.1에서 제안 표·열·제약의 부정 입력과 재열기·일관된 보관을 확인했다. INSERT OR REPLACE의 삭제 trigger 전제와 TEXT NUL의 길이 계산은 별도 반례였으며 BEFORE INSERT 보호와 실제 바이트 길이·NUL 금지로 설계를 수정했다. [sqlite-results.json](evidence/2026-10-14/sqlite-results.json), [SQLite 충돌 처리](https://www.sqlite.org/lang_conflict.html), [문자열 길이](https://www.sqlite.org/lang_corefunc.html#length), [NUL 설명](https://www.sqlite.org/nulinstr.html). 표의 일관성 확인이며 제품 저장기의 해시·JCS·실행 판정 검증을 대신하지 않는다.

Node 저장/HTTP와 순수 검증의 공개 진입점 분리는 [Node package exports 공식 문서](https://nodejs.org/api/packages.html#package-entry-points)를 근거로 선택했다. 실제 설치한 패키지의 import·브라우저 확인은 구현 단계 G1의 필수 조건이며 이 설계 실험에 포함하지 않는다.
