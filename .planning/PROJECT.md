# 개발팀용 CRDT·동기화 검증 요구사항

## 목적과 상태

개발팀이 자기 CRDT·동기화 구현과 업무 규칙을 연결하고, 장애 조건의 실패를 재현하여 자동 검사에 연결하는 도구로 발전시킨다. 사용자가 이 목적을 직접 선택했다. 학습 화면은 결과를 설명하는 보조 기능이다.

현재 구현은 `92ebbea`의 자체 OR-Map 실험기다. 목표 기능의 구현 완료를 뜻하지 않는다. 기준 파일과 해시는 `evidence/2026-10-14/baseline-manifest.json`에 둔다. 이 문서는 목표 정본이며, 기술 결정은 [DESIGN.md](DESIGN.md), 공식 근거는 [RESEARCH.md](RESEARCH.md), 3심 판정은 [REVIEW.md](REVIEW.md)에 둔다.

## 사용자와 실제 사용 절차

| 사용자 | 필요한 결과 |
| --- | --- |
| CRDT·동기화 개발자 | 실제 구현의 변경·메시지를 장애 조건에서 검사 |
| 응용 개발자 | 수렴 외에 자기 업무 규칙의 위반을 검출 |
| 자동 검사 담당자 | 명령 종료 코드와 공유 가능한 실패 파일 |
| 결함 분석 담당자 | 실패 시각·규칙·대상 버전·상태 차이 확인 |

완료할 절차는 “설치 → 실제 대상 연결 → 규칙 등록 → 검사 → 실패 파일 공유 → 별도 과정에서 같은 실패 재생”이다. 첫 실제 대상은 기존 OR-Map과 Yjs 원시 변경이다. 전달 조건과 연결 상태가 다른 Automerge sync는 별도 연결·재연결 검증 이후 검토한다. [RESEARCH S04/S06–S13]

## 첫 지원과 제외

| ID | 사례 | 규칙 |
| --- | --- | --- |
| U01 | OR-Map의 분할·손실·중복·제거·복구 | 수렴, 관찰한 제거, 동시 변경 보존 |
| U02 | Yjs Map의 독립 변경·상태 교환 | 완전 전달 후 값 일치, Yjs 자체 충돌 의미 |
| U03 | 사용자가 주입한 동기식 연결·검사 | 결정적 초기화·완전한 명세·허용 전달 조건 |
| U04 | 자동 검사의 정상·의도적 오류 대상 | 비영 종료, 실패 원인, 재생 파일 |
| U05 | 동료가 전달받은 파일의 재생 | 같은 실패 규칙·사건·상태, 파일 무결성 |

U03은 모든 외부 구현을 지원한다는 약속이 아니다. 동기식 명령·메시지 API, 결정적 초기화, JSON 관찰값, 등록한 전달 조건이 전제다. 명령형 실행기는 자기 자식 과정의 기한 초과를 inconclusive로 처리한다.

새 CRDT, 운영 동기화 서비스, 실제 서버 장애 유발, 계정·조직·과금, 다중 사용자 결과 서버, 여러 언어 실행기, 완전 상태 탐색기는 제외한다. 실제 사용 사례가 확인되면 요구를 변경하고 다시 검토한다. [RESEARCH S02–S05/S08]

## 확정 기준과 변경 기록

1심은 목적·대안·공식 근거, 2심은 반례·자료·자원·호환성, 3심은 수정된 문서·실행 근거·열린 중요 지적을 검토한다. 담당·반례·처리·결론을 REVIEW.md에 기록한다. 중요 지적이 열려 있으면 설계를 확정하지 않는다.

100점이나 모든 결함의 부재를 선언하는 대신 합격 조건과 증거 범위를 기록한다. 외부 제품보다 우수하다는 표현은 같은 과제의 비교 실험이 있을 때만 사용한다. [RESEARCH S03]

2026-10-14: 기존 검사 확대 목표를 실제 대상 연결·실패 재현·자동 검사 연결로 수정했다. 가상 시간·공유 실행 코드·선택 저장·브라우저 독립 실행을 계승했다. 사용자의 목적 선택, 공식 조사, 현재 결함 재현과 실제 Yjs 연결 실험을 근거로 삼았다.

2026-10-14 3심: 명령의 명시적 수락 결과와 전체 순서쌍의 신뢰 복구·완료·무효화 규칙을 보강했다. 메시지 없는 명령의 해석 차이와 dropRate=1의 복구 판정 차이를 근거로 삼았다. 제품 합격 범위는 확대하지 않았다.
